# Inspection controller

The optional inspection controller shares a durable PostgreSQL queue across Compose and Kubernetes. It preserves one isolated execution process per inspection. Ordinary deployment supervision continues through the existing worker or supervisor Jobs.

## Scheduling and waiting

Transactions changing inspection state publish opaque run or sandbox identifiers through PostgreSQL `NOTIFY`. Each API process has one `LISTEN` connection and lightweight request futures. Consumers subscribe before reading durable state, reread after every notification, and reconcile after reconnecting. Notifications carry no source, credentials, authorization decisions, or results. PostgreSQL remains authoritative. See the [PostgreSQL LISTEN guidance](https://www.postgresql.org/docs/18/sql-listen.html).

Controllers reserve capacity under a database advisory lock. Run ownership and assignment leases fence competing controllers. After uploading its encrypted result, an inspection sends an authenticated completion signal using its existing claim capability. The API validates the current assignment and deadline before notifying the controller. The controller reads the encrypted artifact and completes the durable run without waiting for Docker or Kubernetes inspection, log retrieval, or container teardown. Bounded logs are retrieved during background cleanup. Failed cleanup retains its capacity reservation and retries per sandbox. Docker container events and Kubernetes Job watches also trigger completion checks and provide a fallback when the completion signal is interrupted. Interrupted streams reconnect and cause reconciliation. A 30-second recovery scan handles missed notifications, abandoned ownership, expiration, and retention. The ordinary worker's two-second cadence is unchanged. Idle sandboxes make an authenticated 25-second long-poll request to the API; these requests wait on the shared notification listener.

The current limits are 15 ready sandboxes at idle, 15 active inspections, and 30 ready, starting, active, or retiring sandboxes in total across all controller replicas. The proposed total of 19 left too little replenishment capacity during local burst tests. Replenishment creates up to eight sandboxes concurrently per controller. Startup and cleanup run in bounded background executors; retiring resources retain their capacity reservation until removal succeeds. Sandboxes advertise readiness only after importing the execution libraries. They start without user inputs or credentials, accept one expiring assignment, use the existing one-use claim and encrypted artifact protocol, and exit. They are removed after completion or failure and never receive a second assignment. Idle sandboxes expire after 15 minutes. The API registers the desired execution image; old controllers drain active inspections and stop replenishing the old image.

Inspection sandboxes request 100m CPU and 256 MiB memory in Kubernetes and have limits of one CPU and 512 MiB. Docker applies the same CPU and memory limits; it has no equivalent reservation. These limits require workload validation.

## Editor and input reuse

The editor retains its 400 ms debounce. Automatic requests include a random editor identifier and increasing generation. The server scopes these to the authenticated principal, stack path, repository, environment, and operation. One generation can execute while one latest generation waits. Older queued generations are cancelled atomically. Running inspections finish, but obsolete results are rejected with an `inspection_superseded` diagnostic. Reviews receive priority over independent source rendering; selection balances active work across principals.

Independent source rendering runs while the Review view is visible or source output is explicitly requested. A review's source is reused only when all authored inputs, including layout, match. Failed review does not disable independent source rendering.

Immutable repository inputs and catalog metadata are encrypted in artifact storage. Cache keys include principal, repository snapshot, effective configuration and dependency revisions, environment revision, and execution image. GitHub references are resolved to commits, with authenticated access checked even for already pinned commits. Unknown dependency graphs, templates, and registry-hosted module dependencies bypass reuse because their immutability and current authorization cannot be established. Terraform provider declarations remain covered by the configuration revision, but provider binaries do not enter the inspection dependency graph because inspection does not download them. Environment inspections reuse inputs only when runtime discovery proves that the selected environment consumes the direct stack with no additional runfile configuration or variables. Other environment inspections remain correct but may be slower; their latency must be measured separately before claiming coverage of the latency target. Draft authoring and association resolution always run anew. No execution process is reused.

Credentials are delivered anew per inspection. Access and configuration checks run before submission and before accepting results. Dependency references are checked again after execution. Pull requests always perform a fresh review and retain the existing remote revision checks. GitHub GET responses may use a bounded process-local ETag cache, separated by a hash of the full request identity. Every use still sends an authenticated conditional request; denied responses discard cached content. See [GitHub conditional request guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests).

## Rollout and observation

The feature defaults to disabled. Apply migration `0007`, rebuild the API/controller and execution images, then restart the relevant components. Compose uses `STACKSMITH_PLATFORM_INSPECTION_CONTROLLER_ENABLED=true` with the `inspection-pool` profile; `poe stack-up` selects that profile automatically from `.env`. Helm uses `inspectionPool.enabled=true`. The chart creates the shared controller Deployment and its execution Job/watch RBAC. New controller jobs are excluded from the legacy worker even during a mixed rollout.

Do not enable the new path for a deployment until its own acceptance run passes. Rollback should stop new submissions, allow active inspections to drain within their existing deadlines, stop the inspection controller, and disable the feature. Remove unused test sandboxes only after draining. The additive schema can remain in place.

`/api/ready` includes the notification listener when pooling is enabled. Administrator-only `/api/inspection-status` reports controller heartbeat, ready, launching, retiring, active, pending, superseded, cache entries, global limits, and per-process GitHub counters. Controller readiness uses its durable heartbeat. Review logs contain queue, total, preflight, runtime, completion, graph, and execution stage durations without sources or credentials.

## Capacity acceptance

Run Compose and Kubernetes separately on the complete-platform reference budget of 8 vCPU and 16 GiB. Use 15 distinct editor sessions, three with source visible, and representative stacks spanning 1 to 25 components. Begin each editor's first edit immediately after its initial inspection. Continue for ten minutes with edits every 20 to 60 seconds and five simultaneous 15-editor bursts. Include 400 ms debounce in review latency; report initial loading separately.

The authenticated runner is `python -m scripts.benchmark_inspections`. Supply `--url`, `--cookies` pointing to a private JSON array of temporary session cookies, `--repository`, `--observer-container`, and `--report`. Add `--environment` and `--environment-users` to mix environment and preview requests across the component range. The serverless fixture uses the example AWS stack's IAM policy, one execution role, and Lambda consumers. It verifies submitted source and the exact expected managed edges. `--workload policies` retains the simpler policy-only diagnostic fixture. Cookies must belong to authorized test users; the runner does not grant access or create pull requests. Use separate principals when validating live tenant fairness and isolation. Unit tests also exercise distinct principals.

Require p95 review latency below five seconds, no growing backlog, no failed or incorrect accepted results, no OOM events, and at least 20 percent measured memory headroom. Record maximum and initial latency, CPU, queue delay, GitHub requests and conditional hits, and PostgreSQL activity. The runner observes the complete Docker VM, conservatively including unrelated workloads, and records the actual memory budget. Runtime-specific OOM checks and restart/reconnect exercises supplement the load report. A smaller local machine is useful for finding regressions but does not establish a passing 16 GiB reference configuration.

Passing configurations and measured results must be recorded before replacing the legacy scheduling path. The five-second target is not relaxed when a run fails.
