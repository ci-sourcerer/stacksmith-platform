# Database migrations

Stacksmith Platform owns its Alembic configuration, revisions, database tasks, and debug Adminer integration. The same packaged revision history serves PostgreSQL deployments and SQLite authoring/test databases. Generic image builds, formatting, linting, and tests still use common-python-tasks; none of its FastAPI tasks or templates are loaded.

## Apply revisions

```sh
uv run poe run-db-migrations
uv run poe run-db-migrations --no-build
```

The default builds the Python image from current source, waits for PostgreSQL, upgrades to `head`, and refreshes API/worker grants. `--no-build` uses the prepared image. PostgreSQL remains running on completion or failure. A failed upgrade prevents grants and dependent startup. Compose startup runs the same migration service, and Helm runs `stacksmith-platform-init --grant-roles` before installation or upgrade. API and worker database roles have no schema creation privileges.

The installed `stacksmith-platform-init` command requires only `STACKSMITH_PLATFORM_DATABASE_URL`, using a PostgreSQL administrator connection. It does not load GitHub or execution configuration. Project Compose tasks still require the configured single `.env` because Compose interpolates the full deployment model.

## Author and check revisions

Apply all existing revisions before editing the schema. Edit SQLAlchemy metadata, then generate and review the proposed operations.

```sh
uv run poe create-db-migration --message "Add a repository field"
uv run poe create-db-migration --message "Backfill repository values" --empty
uv run poe run-db-migrations
uv run poe check-db-migrations
```

Authoring and checking build the development image and run against current mounted source. Generated revisions appear in `src/stacksmith_platform/migrations/versions` with timestamped names and Ruff formatting. The task uses the host UID/GID so files remain writable. PostgreSQL stays private; no host database port is required. Authoring refuses databases behind or ahead of the checked-out revision head. `--empty` creates a revision for manual operations. Autogenerated changes require review, especially renames, data transformations, and downgrades. Commit the model changes and revision together.

`check-db-migrations` requires the database at the checked-out head and fails when metadata would generate additional operations. It does not apply migrations. When adding PostgreSQL-specific operations, retain SQLite equivalents or use Alembic batch operations so local authoring remains supported.

For advanced Alembic commands against the local database, prepare the development image with `uv run poe platform-image --debug`, then use the tools service.

```sh
docker compose -f compose.yaml -f compose.migrations.yaml run --rm --no-deps --entrypoint alembic migration-tools current
docker compose -f compose.yaml -f compose.migrations.yaml run --rm --no-deps --entrypoint alembic migration-tools history
```

The same runner accepts `upgrade head` and `downgrade REVISION`; downgrades can remove data and do not refresh role grants. Offline SQL can also be generated with `STACKSMITH_PLATFORM_DATABASE_URL` set to a PostgreSQL URL and `uv run alembic upgrade head --sql`.

## Local database tools

`uv run poe db-shell` starts PostgreSQL if needed, waits for health, opens psql, and leaves the database running. `uv run poe stack-up --debug` also starts Adminer at <http://localhost:8081>, with automatic login as the local database administrator. Set `STACKSMITH_PLATFORM_ADMINER_PORT` to change the port. Adminer binds only to localhost and is absent from production Compose and Kubernetes deployments.

To start only the database UI and its database dependency, use `uv run poe stack-up --debug --service adminer`. Repeat `--service` to select more services. Selected startup builds only required application images, and foreground exit cleans up the selected services and their dependencies. Detached mode leaves them running until stopped.

`uv run poe reset-db` stops the local stack and deletes only the PostgreSQL volume resolved by Compose. It refuses external database volumes and preserves artifact volumes and `.env`. The next `stack-up` or `run-db-migrations` recreates PostgreSQL and applies the baseline. Existing artifact files remain, but a reset discards their database records.

## Fresh-baseline transition

The first Alembic revision defines the baseline; later revisions evolve it. Always upgrade to `head` rather than treating the baseline as the current schema. Databases created by the old initializer are intentionally unsupported and rejected without changing their contents. For disposable Compose data, explicitly run `poe reset-db` and then restart. For local SQLite authoring, stop the application and move aside its configured database file before restarting. Preserve any data you need before doing so. Hosted PostgreSQL requires an explicitly provisioned fresh database; do not stamp an old schema as current.

## Ownership and future extraction

Project-owned stack lifecycle and debugging, secret configuration, database shell/reset, Alembic execution/authoring, and debug Adminer cover the shared FastAPI concepts. The existing single `.env` replaces the shared multiple-file override interface. Runtime migration resources live with the Python package; development orchestration lives under `scripts`, and deployment wiring stays in Compose and Helm. These boundaries support a future framework or template extraction without introducing one now. Adapted code is attributed in the repository's third-party notices.

## Verify changes

Run `uv run poe format`, then `uv run poe lint` and `uv run poe test`. The regular suite covers SQLite migrations, drift detection, task behavior, and rendered Compose/Helm configuration. Set `STACKSMITH_PLATFORM_TEST_DATABASE_URL` to a disposable PostgreSQL database to exercise the migration round trip in an isolated schema.

The container checks require prepared production and debug images tagged `stacksmith-platform:migration-test` and `stacksmith-platform:migration-test-debug`. Build them with `poe platform-image` and `poe platform-image --debug`, then tag the resulting images with these test names. Run the checks with the following command.

```sh
STACKSMITH_TEST_MIGRATION_IMAGES=1 uv run python -m pytest tests/test_migration_containers.py
```

These checks create isolated PostgreSQL and Adminer containers, verify packaged migrations and grants, generate a revision in a temporary checkout with the host UID/GID, and exercise automatic Adminer login. Test containers, anonymous database volumes, and networks are removed afterward.
